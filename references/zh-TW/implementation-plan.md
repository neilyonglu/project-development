# 實作拆解與順序確認

本文件為中文閱讀版；代理執行時使用上層英文同名指引。輸出語言依英文入口的設定，中文模式使用繁體中文，技術識別字保持原樣。

將已整理的需求、資料模型、操作流程、介面契約與驗收情境轉成具體開發工作。此階段交付計畫，不因拆解工作而修改功能、操作 DB 或開始執行測試。

先沿用 [專案脈絡](project-context.md) 的模組邊界、工作文件與驗證方式；新增依賴或偏離既有架構需記錄需求理由與較簡單替代。

## 現況與缺口

讀取同一 issue 的分析及相關設計，核對工作區現有程式。區分已具備、需要修改、需要新增與待確認；有程式或測試檔不代表功能已驗證完成。標明核對依據與驗證狀態，避免重做既有能力。

## 工作項目

依可獨立實作與驗證的行為拆解，避免只按檔案列待辦，或把整個功能放在一個無法判斷完成的項目中：

| 工作項目 | 現況與要達成的行為 | 沿用／修改／新增的 module 或檔案 | 相依項目 | 完成條件／驗收案例 | 阻擋事項 |
|---|---|---|---|---|---|

- 每項說明為什麼需要、實際改動邊界，以及對應的需求或缺口；尚未確定的檔案位置標為預計，不假裝已存在。
- 完成條件引用原文件的具體驗收案例，說明應驗證的行為，不以「程式已寫完」或「編譯成功」取代功能完成。
- schema、設定、權限與跨層契約若是前置條件，列入相依；涉及既有資料或新舊版本共存時，交代必要的相容順序。
- 未解需求只阻擋受影響項目。可獨立完成的工作仍列出，不自行決定尚未確認的業務政策。

## 順序與第一步

依實際相依及現有完成程度安排順序，優先形成能驗證的完整操作路徑；不強制所有 issue 都從 DB 或後端開始。標出可獨立進行的項目，但不因計畫而自行啟動平行 agent。

明確指出第一個可開始的項目、要改的位置、採用此順序的理由及完成條件。若目前沒有可開始的項目，列出使它可開始所需的具體決定。

## 交付與銜接

在原 issue 文件補上實作拆解與順序，依專案脈絡維持工作文件單位，引用既有設計及驗收案例。計畫內的待實作項目與已完成／已驗證結果分開記錄。

使用者要求逐項說明時，一次解釋一個工作項目。計畫確認不等於授權執行；使用者明確要求開始建構或實作後，再依授權範圍進行。

使用者要求開始開發時，銜接 [實作與驗證](implementation-validation.md)，持續完成授權範圍並記錄驗收結果。
