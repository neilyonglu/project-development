# 專案脈絡整合

本文件為中文閱讀版；代理執行時使用上層英文同名指引。輸出語言依英文入口的設定，中文模式使用繁體中文，技術識別字保持原樣。

先理解這個專案如何開發，再將 project-development 的階段流程套用到本次需求。保留使用者的流程邏輯；專案脈絡是可核對的摘要和來源索引，不是取代原規範的新規章。

## 建立與沿用

1. 確認 repository、工作範圍與適用的 AGENTS.md、CLAUDE.md、專案說明及規範；核對最近似的實際模組、manifest、build scripts 與 CI。
2. 找出既有專案脈絡或等效文件，沿用其位置；沒有時放在專案慣用文件目錄，例如 `docs/development/project-development-profile.md`。文件留在專案，skill 發行包不帶入使用者的實際專案資料。
3. 首次建立足以支援當前工作的摘要；標記未核對範圍，之後按需要補充。既有脈絡只刷新本次涉及或已變動的項目，不要求全專案掃描完成才動手。

## 整合內容

| 類別 | 要整理的專案特點 | 如何影響流程 |
|---|---|---|
| 架構與模組 | 技術、實際目錄、模組責任、跨層呼叫和最近似範例 | 決定沿用位置與必要配套，避免建立第二套架構 |
| 資料與契約 | DB／migration、資料存取、權限、錯誤、精度／時間、metadata 等慣例 | 指向本專案的設計與正確性核對方式 |
| 需求與文件 | 平台與來源、issue／feature 工作單位、命名與文件位置 | 決定各階段更新哪份工作文件，及需求如何追溯 |
| 工作與交付 | 分支、比較基準、審查、QA、CI 觸發、升級／發布順序 | 決定銜接條件；規範記載流程不代表使用者已授權外部操作 |
| 驗證 | build／lint／typecheck／測試指令、fixture、目標環境與副作用 | 決定有意義且可執行的檢查，不以通用範例替代 |
| 輸出語言 | 使用者明確選擇或 `output_language: zh-TW / en` | 英文工作指令共用，交付使用所選語言 |
| 可用依賴 | CLI、skills、plugins、瀏覽器、runtime、網路及必要存取 | 記錄所需能力、可用／未核對／缺少／不適用，以及替代或阻擋範圍 |

每項附來源、適用模組、核對日期與狀態。區分使用者已確認慣例、規範要求、程式現況、實作建議與待確認。版本以相關 manifest／執行結果核對；較新的文件不自動代表業務核准。不要保存憑證、秘密或正式資料。

## 在階段中使用

- 工作文件引用本專案脈絡；issue 分析仍採五項架構，不把共用特點複製進每個 issue。沒有 issue 時以需求名稱與來源辨識工作。
- 設計與實作沿用專案實際的業務入口、服務、代管平台及文件慣例。例如範例商店專案可能有訂單 API、通知服務與一個 issue 一份文件；其他專案由自身來源決定，不能套入別的專案的 API 或欄位。
- 階段開始時核對輸入是否足夠、使用者授權範圍和所需能力；結束時記錄產物、證據、未解問題及下一項可做的工作。已有跨階段授權就繼續，不因階段完成重新詢問相同授權。
- 發現需求／契約缺口時，回補受影響的設計與案例；測試或審查發現問題時，回到相關實作。只重新核對受影響範圍，維持原文件與追溯關係。
- 外部審查 skills 適用且可用時優先使用，否則按 [審查與交付](review-delivery.md) 的兩輪目標自行核對，記錄實際方式。缺少遠端需求存取時可整理已提供資料，但不能宣稱完整讀取；必要 runtime 或測試 DB 缺少時標記未驗證。
- 新增層、套件、表或工具前，指出本期需求、既有能力為何不足與較簡單方案；必要的偏離及理由記錄在工作文件，不建立形式化必填報告。

## 更新時機

框架、目錄、規範、CI、工具或交付慣例改變時刷新相關段落，保留重要決定與來源。未變動項目沿用，不把每個工作當成重新初始化專案。脈絡存在不代表所有能力已驗證，也不代表產品功能已驗收。

公開文件、範本與示範一律使用虛構或中性名稱，不使用公司內部名稱、真實內部 issue 或實作案例。實際專案脈絡留在其專案內，不複製到公開 skill。
