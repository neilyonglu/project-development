# 實作與驗證

本文件為中文閱讀版；代理執行時使用上層英文同名指引。輸出語言依英文入口的設定，中文模式使用繁體中文，技術識別字保持原樣。

使用者要求開始開發時，依已確認的計畫實作並驗證授權範圍。只要求理解、設計或規劃時，不啟動此階段。開始後持續完成該範圍，不為例行可逆修改逐步詢問；部署、遠端發布與實際 DB 套用仍依各自授權處理。

## 選定工作與核對現況

讀取同一 issue 的實作計畫、需求、相關設計及驗收案例，依相依順序選定工作項目。核對適用專案規範、現有程式與使用者尚未提交的修改；保留無關異動。沒有正式計畫但工作範圍已清楚時，完成必要核對即可，不要求補齊所有前置文件才動手。

## 實作

- 依具體行為完成所需改動，沿用既有 module、介面、資料存取、錯誤處理及 schema 升級方式，避免重建已存在的能力。
- 跨層項目核對必要的 UI、後端入口、設定、資料模型與 metadata／migration 配套，避免單層完成卻無法使用。
- 不以固定成功回應、吞掉錯誤或跳過權限／資料限制，讓未完成流程看似可用。
- 發現需求矛盾或設計缺口時，記錄依據及影響，回補原 issue 文件。可由既有需求與慣例決定的例行細節直接處理；影響業務政策的未解問題只阻擋相依工作，提出具體問題並繼續獨立工作。

## 建立程式碼的基本要求

撰寫時就核對下列事項，不留到審查階段才整理；適用於本次新增與修改的程式，不擴大成全專案重構。

- **參數確實有用途**：檢查函式參數、React Props、設定與傳遞欄位是否真的被讀取並影響預期行為。移除本次不需要的參數及無效傳遞，同步更新呼叫端、型別與相關說明。不為「之後可能用到」保留可選參數或開關。
- **先確認再刪除**：追查呼叫端、callback／框架介面及動態使用，不能只因函式內沒有引用就刪掉必需的簽名。介面要求保留但刻意不使用的參數，依專案慣例標示理由。
- **名稱能說明意義**：變數、參數、函式、類別與檔名應表達業務角色或實際行為。避免意義不明的縮寫與泛稱；局部短迴圈變數可依慣例使用。對含糊名稱先釐清資料來源與用途，再改名，不猜測業務語意。
- **同一概念使用一致名稱**：沿用已確認的需求術語與專案慣例；不同概念不要共用容易混淆的名稱。數值有比例、百分比、時間或數量差異時，讓名稱、型別或明確說明能辨識單位。布林值應表示清楚條件，避免難讀的雙重否定。
- **簽名與預設值清楚**：區分必填、可選、NULL 與預設值；不要用多個位置型布林參數讓呼叫難以理解。參數過多時先檢查是否混合責任，再依實際需要整理，不為縮短簽名新增無意義抽象。
- **程式結構容易追讀**：函式責任集中，控制過深巢狀，重複邏輯先尋找既有工具。移除未使用的 import、變數、函式、不可達分支與過時註解；必要說明交代業務理由或限制，避免只重述程式。
- **改名不破壞契約**：內部改名同步更新所有使用位置；API、DB 欄位、設定 key 或公開介面改名須核對使用者、資料與相容性，不能當成純文字整理。必要時保留契約名稱並在內部清楚映射。

利用專案現有 lint、型別檢查或編譯找出可自動辨識的問題，並人工核對語意；檢查通過不代表名稱或參數用途已清楚。

## 實作時的正確性檢查

依本次操作、資料與風險核對下列項目；記錄適用項目的處理方式及待確認問題，不要求每個 issue 都新增鎖、版本欄位、重試或監控系統。先確認既有機制是否足以支援需求。

- **資料一致性與交易**：列出一次操作涉及的寫入及交易／提交邊界，確認哪些必須一起成功。失敗時不可留下無法辨識的半完成資料；跨服務無法共享交易時，明確表示已提交與待執行狀態及恢復方式，不承諾不存在的原子性。核對主鍵、唯一限制與關聯策略能否維持業務不變條件。
- **併發與重複操作**：核對多人修改、重複提交、排程重疊與執行重試的結果，避免遺失更新或重複副作用。不能只靠前端按鈕停用或「先查再新增」保證一致性；依既有交易、唯一限制、鎖或版本檢查評估必要處理。重試只在操作安全且政策明確時使用，交代可重試錯誤、界限及結果；不宣稱未被機制保證的只執行一次。
- **資料時效**：明確區分畫面快照、決策時資料與執行時資料。寫入前依需求重新檢查權限、限制與必要資料條件；資料改變時應拒絕、要求重新確認或依已核准政策處理，不能自行選擇最新值覆蓋使用者原意。
- **權限與信任邊界**：在後端與真正執行寫入的位置核對身分、dataset／tenant 及操作權限。客戶端傳入的 user ID、dataset、狀態或 target 不可直接作為授權證據；必要時逐項檢查批次目標。區分服務身分與原操作人的權限，不以通過 token 驗證代表可執行所有業務操作。
- **錯誤與資源管理**：依呼叫方式核對 timeout、取消、例外、連線／session／檔案釋放及交易回滾。保留可辨識的失敗類型與必要追查資訊，不吞掉錯誤後回成功；部分完成須呈現已完成與未完成項目。記錄不得洩露 token、密鑰或不必要的敏感資料，避免為每次錯誤重複建立額外抽象。
- **資料量與效能**：依預期使用規模核對查詢次數、N+1、索引依據、無上限載入、批次大小與記憶體使用。同步／非同步處理避免阻塞不適合的執行環境；查詢、分頁或批次調整需保留結果語意。先用實際路徑與資料量定位問題，不為猜測的效能需求新增快取或複雜系統。
- **測試有效性**：測試應能區分正確與錯誤行為，核對有意義的輸出、資料變化、限制及副作用，不只驗證 mock 被呼叫或重述公式。辨識 mock 掩蓋的 DB 限制、交易、併發與跨層問題，依風險選擇必要的真實整合驗證。資料與時間條件可重現，既有測試通過也不能代替未覆蓋的案例。
- **升級與相容性**：涉及 schema、介面、設定或狀態變更時，核對舊資料、舊設定及新舊服務共存的行為，交代部署／升級順序、必要回填與失敗恢復。相容處理要有真實使用依據，不永久保留無人使用的雙重契約；無法安全回滾時明確說明限制。
- **前端狀態與操作體驗**：涉及畫面時，核對載入、空資料、失敗、未儲存及部分成功的呈現與可操作狀態。提交失敗應依需求保留輸入並提供恢復途徑；較早請求的回應不可覆蓋較新的操作結果。必要的欄位標籤、鍵盤操作與狀態提示沿用既有元件慣例，不只檢查成功畫面。
- **精度與時間邊界**：核對數值單位、精度、捨入位置、比較門檻，以及日期／時區／週期起訖在 DB、後端與前端一致。區分顯示格式與計算值，避免顯示捨入改變業務判斷；週期與業務日期使用已確認的日曆語意，不猜測 ID 的意義。
- **外部資料與依賴**：驗證外部回傳的格式、必要欄位、有效值與版本相容性，不以 HTTP 成功代表資料可用。對缺欄位、未知值或不支援的格式提供可辨識結果；fallback 只能採已確認政策，不能默默捏造業務資料。新增依賴先核對專案版本與既有能力，不為單一用途引入不必要套件。

將適用檢查對回原 issue 的介面、資料設計與驗收案例。發現未定義的交易、併發或時效政策時列為待確認，不用技術偏好替需求決定。未驗證的機制及結果明確標示，不因程式結構整齊而推論可靠性。

## 驗證

對照已確認的驗收案例選擇適當檢查，優先驗證改動的行為、邊界與相關失敗情境。依影響範圍執行必要的編譯、型別檢查、單元或整合測試；不為低影響可逆修改強制新增測試，也不寫只重述實作的測試。

執行前核對 fixture、目標環境與外部服務副作用。真實 DB、schema 重建或付費模型呼叫須在適當授權與環境下進行，不因存在測試檔就直接執行。不得把 mock／離線通過推論成真實 DB 或端到端已通過。

失敗時判斷是改動問題、既有問題或環境限制；修正授權範圍內的問題後重跑受影響檢查。必要檢查通過後，除非有新改動、失敗或未解疑慮，不反覆擴大測試。

## 完成與交付

在原 issue 文件更新工作項目的實作與驗證結果，依專案脈絡維持工作文件單位。記錄實際改動、執行的檢查及結果、未驗證部分與原因，以及剩餘工作；schema 的宣告、套用與驗證狀態分開。

最後一次修正後同步核對受影響的介面說明、欄位設計、設定說明、驗收案例與架構圖。以最終程式為現況依據，需求與實作不同時保留差異，不直接改寫需求來掩蓋不符合。文件的已驗證狀態須有最終相關版本的實際證據：記錄驗證時間、branch／HEAD 及相關未提交狀態、指令、退出碼與結果摘要。證據之後若改動受測行為，原結果不代表新版本通過；重跑受影響檢查。

交付說明完成了什麼行為、如何驗證及實際限制。有程式或測試檔不代表完成；僅在工作項目的完成條件已滿足時標記完成。不得因完成本項自行開始下一個未授權階段、部署或發布。

使用者要求整理及審查時，銜接 [審查與交付確認](review-delivery.md) 的第一步，依序進行程式碼整理與雙重審查。
