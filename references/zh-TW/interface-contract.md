# 介面契約確認

本文件為中文閱讀版；代理執行時使用上層英文同名指引。輸出語言依英文入口的設定，中文模式使用繁體中文，技術識別字保持原樣。

在操作流程清楚後，確認跨 module 呼叫及前端元件如何交換資料。此階段交付說明與設計；不因確認契約而修改功能、執行測試或操作 DB。

## 依據與範圍

讀取同一 issue 的需求、操作流程及相關資料模型，沿流程挑出實際需要的介面。既有介面查閱呼叫端、接收端、型別與驗證程式；新增介面依需求提出契約。標明現有實作、建議設計與待確認事項，不把型別宣告當成執行時已驗證。

## 逐個介面說明

每個介面交代呼叫端、接收端、用途與觸發時機，並列出實際入口：API method／path、RPC method、函式或元件 Props；依專案既有呼叫慣例，不一律改成 REST。

輸入與輸出分別提供欄位表：

| 欄位 | 意義 | 型別／允許值／單位 | 必填與缺省／NULL 語意 | 來源或計算責任 | 驗證規則 |
|---|---|---|---|---|---|

- 身分、dataset、權限及設定交代來源與檢查位置，不假設客戶端傳入的識別資訊可信。
- 說明成功、無資料、驗證失敗、權限不足及流程實際可能發生的受阻／失敗結果，包含錯誤格式與呼叫端如何處理。
- 涉及批次或非同步時，區分請求已接受、決策已保存與執行已完成；說明逐項結果及部分成功如何表達。
- 流程涉及重複提交、重試或契約變更時，核對既有處理方式及相容性；未確認則列為問題，不自行增加版本或重試機制。
- 涉及數值或時間時，明訂單位、精度／捨入、時區及起訖邊界；外部資料另說明缺欄位、未知值及格式／版本不相容如何辨識，不能只定義成功連線。

## 前端資料與 Props 對應

涉及畫面時，將回傳資料對應到元件的值、選項、可操作狀態與顯示標記，說明由哪一層轉換或計算，以及事件 callback 將觸發哪個操作。可選 Props、預設值與停用行為須核對元件實作；註解表達的意圖與實際行為有差異時明確列出。

不要求 DB 欄位、API 欄位與 Props 一對一；交代必要的轉換與責任，避免在多層重複判斷同一業務規則。

同時確認載入、空資料、錯誤、未儲存及部分成功所需的資料與操作行為，依 [實作時的正確性檢查](implementation-validation.md#實作時的正確性檢查) 中的相關規則確認設計。

## 交付與銜接

在原 issue 文件補上介面契約段落，依專案脈絡維持工作文件單位。將契約對回操作流程、module、DB 欄位與 UI 行為，列出已一致、缺少定義與彼此衝突的部分。使用者要求分段說明時，一次解釋一個介面。確認契約後，依使用者授權再銜接建構或實作。

使用者要確認不同情況下的正確結果時，銜接 [業務規則與驗收情境確認](business-acceptance.md)，將規則轉成具體案例。
