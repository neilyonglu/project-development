# 專案雛形建構

本文件為中文閱讀版；代理執行時使用上層英文同名指引。輸出語言依英文入口的設定，中文模式使用繁體中文，技術識別字保持原樣。

將已確認的需求架構落成可開始功能實作的程式結構。若涉及資料庫，同時準備必要的資料模型與 schema 變更檔。

## 輸入與範圍

先讀取該 issue 的分析、適用專案規範與最近似的既有模組。確認需求架構、module 異動、本期範圍，以及會阻擋建構的待確認問題。沒有 issue 時，依使用者提供的需求與架構工作，不自行創造 issue。

建構要求授權必要的本機骨架、設定與 migration 檔案；若只要求設計，交付具體方案，不直接建構。資料庫實際套用須確認目標環境、既有授權及副作用，不能把寫出 migration 視為已建立資料表。

使用者要熟悉專案、討論框架或確認 DB 設計時，先交付專案理解與建構方案，不執行建構、測試或 DB 操作。依使用者目前要求的深度逐步說明；明確要求實際建構後才進入第 2、4、5 項的執行工作。

## 1. 確定框架與模組邊界

- 新專案依需求、部署環境與限制選擇框架；既有專案先確認並沿用實際框架、依賴版本、目錄與模組慣例。
- 指出需求架構各部分對應的 module、入口、呼叫關係與介面。沿用／修改／新增分清楚，不為骨架新增未被需求使用的抽象層。
- 僅對會影響建構方向的未解決定等待釐清；記錄選擇依據，不把 agent 偏好當成需求。

## 2. 建立必要程式骨架

建立需求需要的目錄、模組入口、介面、設定與啟動方式，沿用既有命名、錯誤處理、身分與資料存取方式。跨層功能核對必要的前端 route／呼叫、後端入口、service／Domo 與 metadata 等配套。

骨架尚未包含的業務算法明確標記為待實作；不可用固定成功回應讓未完成流程看似可用。若需求只涉及既有功能調整，直接補必要結構，不建立新專案。

## 3. 確定資料模型（涉及 DB 時）

先核對既有 schema 與資料語意，列出沿用、修改、新增的表，說明各表如何支援需求。沒有 DB 異動時，記錄無需建表的理由，不建立空表。

對本期需求使用的表逐表說明，包含沿用的表；每張表先交代業務用途、一筆資料代表什麼、由哪個 module 讀寫，以及新增、更新與保留歷史的時機。用一個需求情境解釋它如何與其他表合作，讓使用者能確認資料設計。

每張表提供欄位設計表：

| 欄位 | 業務意義／存在理由 | 型別（含長度／精度） | 可空性與 NULL 語意 | 預設值／產生方式 | 限制／關聯 |
|---|---|---|---|---|---|

- 補充主鍵、ID／sequence 來源、唯一限制的欄位組合與業務理由，以及有查詢依據的索引。
- 關聯說明對應欄位、一對一／一對多等基數，區分邏輯關聯與已宣告的實體外鍵；沒有外鍵時說明如何維持一致性，未確認則標記待查。
- 狀態欄位列出有效值與轉換條件；區分建議、人工決策與執行結果，避免一個狀態被誤解為整個流程已完成。
- 視需求核對 dataset／tenant 邊界、時間欄位的時區與業務日期、資料生命週期與稽核；不把未被需求要求的項目全部加進模型。
- 標示資訊來源與確認程度：需求設計、model、metadata／migration 宣告、實際 DB 驗證。來源不同或缺少定義時列出差異／待確認，不把 Python 型別直接當成 DB 的長度、預設值或限制。

使用者要求逐表解釋時，每次說明一張，等使用者要求下一張再繼續。正式設計仍整理在同一 issue 文件中；skill 保存可重用的設計規則，不固定套用某個 issue 的表名或欄位。

必要時補 ER 圖。涉及既有資料的型別、必填、唯一限制與關聯變更，說明資料轉換、回填與相容性；無法確定資料語意時先釐清，不自行把 NULL 改成零。

使用者理解表格後，要確認一次操作如何串起 module 與 DB 時，銜接 [操作流程與資料流確認](operation-flow.md)，先確認流程，再依實際授權進入建構。

## 4. 建立 schema 變更檔與配套

沿用專案現有 migration、metadata 或 appUpgrade 機制，不另造第二套升級流程。準備可審查的變更檔、需要的模型宣告與必要 fixture，說明套用順序、既有資料處理與失敗恢復方式；不可承諾無法保證的無損 rollback。

將「已設計」「已寫入變更檔」「已套用指定 DB」「已驗證 schema」分別記錄。只有在已授權的目標環境執行升級；若尚未授權，先完成檔案與驗證計畫，再就具體套用動作請求必要確認。

## 5. 驗證最小可執行流程

依實際建構範圍確認必要模組能啟動、介面能連接、設定能讀取；涉及 DB 時，在適當且已授權的環境驗證必要 schema 與資料存取。驗證不得意外連到正式 DB、清除既有 schema 或呼叫付費模型。

不要求所有骨架都有前端或 DB；依需求選擇有意義的基本路徑。骨架啟動或編譯通過不代表業務功能完成。缺少環境時，記錄未驗證部分與可重現步驟。

## 交付與後續銜接

在原 issue 分析文件增加建構進度，保留原五項分析主體，列出框架決定、實際檔案異動、DB 變更與套用狀態、啟動／驗證結果，以及下一步需實作的業務能力。分析需求與骨架落點若不一致，更新相關決定與依據。

交付可供使用者與後續開發者確認的具體結果；不因完成骨架自行開始未授權的功能實作、部署、遠端留言或資料庫操作。
