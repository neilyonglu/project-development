# 審查與交付確認

本文件為中文閱讀版；代理執行時使用上層英文同名指引。輸出語言依英文入口的設定，中文模式使用繁體中文，技術識別字保持原樣。

目前已確認第一步「程式碼整理與雙重審查」與第二步「完善實作架構圖與測試對應」。後續交付步驟待使用者確定後再補，不因本階段自行合併、部署或發布。

## 第一步：程式碼整理與雙重審查

使用者要求審查或整理程式碼時才執行；只討論或修改流程規則時，不開始審查專案程式。

### 1. 確定範圍並整理程式碼

確認本次 issue、變更基準及實際 diff，保留使用者無關異動。改善本次變更的命名、結構、重複邏輯及無用程式，沿用既有能力，保持需求行為與介面相容；不為個人偏好重寫整個專案。

逐項核對 [建立程式碼的基本要求](implementation-validation.md#建立程式碼的基本要求)，尤其追查未使用／只傳遞卻未生效的參數與 Props、意義不明的名稱、單位及術語不一致。需要釐清的業務意義列出問題；參數刪除或改名同步檢查呼叫端與對外契約。

同時依本次功能核對 [實作時的正確性檢查](implementation-validation.md#實作時的正確性檢查)：交易一致性、併發與重複操作、資料時效、後端權限、錯誤與資源管理、資料量與效能、測試有效性及升級相容性。記錄成立的風險與證據，區分已處理、未驗證及待確認，不將純可讀性整理視為正確性已通過。

依同一規則核對前端操作狀態、精度／時間邊界與外部資料契約；並對回需求追溯，確認沒有本期需求遺漏、無依據改動或過時文件。共通要求沿用原規則，不另維護重複清單。

### 2. 正確性審查：優先使用 `/code-review`

先解析執行環境中的同名 command／skill，讀取其實際規則，按本次審查範圍呼叫；不得將名稱相似的 skill 默認為同一個。

若解析到的同名 command 是 GitHub PR 審查，檢查規範遵循、正確性及變更脈絡。執行前核對是否適用於當前平台、PR／MR 或本機 diff。GitLab／本機範圍不得假裝完成 GitHub PR 指令；不適用或缺少執行能力時明確記錄，直接在已授權的本機範圍執行等效正確性審查：逐項對回需求與驗收案例，核對完整變更、失敗路徑及適用專案規範，列出位置、證據、嚴重度與修正建議。不為缺少此 command 停住本機審查，也不自行安裝或發布遠端留言。指令含遠端留言時，依使用者本次範圍及授權處理，不把本機整理與審查當成自動發布留言的授權。

### 3. 簡化審查：優先使用 `/ponytail-review`

優先核對 `/ponytail-review` 的可用名稱與實際 SKILL.md；同名或近似名稱不能證明適用。缺少或不適用時，在正確性審查後自行執行下列簡化審查，記錄為本機等效審查，不宣稱已呼叫外部 skill。

在正確性審查後，對整理後的變更使用適用 skill 或執行本機等效審查，專門找不必要的抽象、依賴、重造標準功能、未使用的彈性與可縮減邏輯。逐項記錄位置、刪減內容、需求證據與替代方式；正確性、權限及效能問題由一般審查處理。此輪先列建議，修正由主流程依已授權的整理範圍執行。

### 4. 處理問題與重新驗證

核對兩輪結果的證據及需求影響，修正範圍內成立的問題；不採用的建議記錄理由，未解問題記錄阻擋程度。刪減不得移除必要業務規則、權限檢查、資料限制或有意義的驗證。

針對整理及修正影響的行為執行適當檢查；沿用 [實作與驗證](implementation-validation.md) 的驗證規則。重大修正後重審受影響部分，不在沒有新問題時無限循環。

## 第一步的交付

在原 issue 文件記錄整理範圍、實際使用的 command／skill、兩輪審查結果、修正／不採用理由與驗證結果，依專案脈絡維持工作文件單位。缺少 skill、平台不適用或未完成的審查明確列出，不用一般檢查冒充已呼叫。

每輪記錄「可繼續／需修正／受阻」、問題位置與證據；無證據的推測列為待查。未解關鍵需求或正確性問題阻擋其相依交付，低風險建議可記錄不採用或延期理由。兩輪無發現不等於需求驗收或發布已完成。完成此步後交代剩餘問題，依既有授權銜接其他交付工作；只在下一動作超出授權或仍有必要未解決定時詢問。

## 第二步：完善實作架構圖與測試對應

在第一步的整理與修正完成後，依最終變更更新架構圖。此圖說明本次實際實作與檔案流程；保留 issue 分析階段的需求架構圖，兩者不同時記錄差異，不把實作當成需求已核准。

### 1. 核對所有變更檔案

使用已確認的比較基準與最終 diff，包含本次相關的 committed、staged、unstaged、untracked 變更，排除使用者無關異動。列出新增、修改、刪除與重新命名檔案；每一項都必須能在圖或配套清單中找到。

先依 [可執行的流程核對](automation.md) 使用 inventory 產生清單，再核對範圍；節點的 `files` 與「沒畫進圖的檔案」清單的 `data-file` 對應每個檔案，完成後使用 coverage 找出缺漏、diagram 檢查結構。保留人工核對節點、箭頭與測試的責任。

執行路徑的檔案以節點呈現；設定、metadata／schema、型別、建置及文件放入適當配套分組，說明支援哪個流程。刪除或重新命名的檔案說明移除／替代關係，不畫成仍在執行。必要的既有依賴可加入圖，但標明為沿用，不假裝本次修改。不得為了連線而虛構呼叫。

### 2. 畫出檔案與資料流程

- 以系統層與責任分組，例如前端入口／頁面／共用元件、後端入口／業務處理／設定、資料層與外部服務；依專案實際結構選擇。
- 節點標示真實檔名或類別名及簡短責任；提供對應路徑，避免同名檔案混淆。
- 主流程由觸發入口追到結果，箭頭標示 method、API、事件或重要資料；跨層呼叫加粗，非同步、設定注入及資料讀寫用清楚圖例區分。
- 納入本次相關的身分、dataset、設定來源與優先順序，以及會影響結果的失敗／受阻分支。複雜流程拆成總覽與細部圖，檔案清單維持完整對照。
- 修改狀態、閱讀／審查狀態與驗證結果分開標示；不能以「已看過」代表已實作或已驗證。

### 3. 納入 testing files

將本次新增、修改或直接驗證本次行為的測試檔畫成獨立測試節點，以虛線連到受測 module／介面，標示測試涵蓋的規則、邊界或失敗情境。區分 mock／單元、整合與端到端範圍；不把測試連線當成產品執行流程。

測試檔存在、已執行、通過、失敗與未執行分開記錄，附第一步的實際驗證結果。沒有對應測試的變更標明驗證方式或缺口，不為使圖看似完整而建立形式測試。

### 4. 提供可閱讀的 HTML 圖

從 skill 的 [範本](../../assets/architecture-diagram.html) 建立，依 [實作架構圖 HTML](architecture-diagram.md) 填入 Mermaid 原始碼、節點說明、Part 分頁與未畫進圖的檔案。範本已提供分層圖、可收合圖例、Part 分頁、顯示／隱藏測試、放大／縮小／重設、Ctrl＋滾輪縮放、hover 說明、點擊卡片（檔案、函式、樣式）與連線高亮，以及明暗背景下可辨識的配色。測試隱藏時只移除測試節點及其邊線，不能破壞主流程或 Mermaid 語法。

使用適合的版面減少線路交錯；圖過密時拆圖，不以縮小文字掩蓋問題。渲染失敗提供可見錯誤；使用外部渲染資源時說明網路需求。開關與縮放偏好可保存，但不影響圖的內容正確性。

### 5. 完整性與交付

將最終檔案清單逐項對回圖節點或配套說明，核對箭頭與實際程式呼叫、DB 讀寫及測試目標一致。驗證 HTML 能渲染、測試開關及縮放可用；未能實際驗證時明確記錄，不宣稱已通過。

原 issue 文件連到這份架構視圖並記錄比較基準、涵蓋範圍及未解差異；HTML 是同一 issue 的配套視圖，不另建立第二份 issue 分析。規則本身自足，不依賴會被刪除的範例 HTML 或其連結。
